# 每日生产巡检与待办梳理

- 状态：采用
- 日期：2026-11-17
- 关联：Issue #95、`.github/workflows/patrol.yml`、`.github/workflows/patrol-daily.yml`、`patrol.py`

## 背景

现有部署验收会检查页面是否可用，但只在部署时运行。生产环境出现过偶发首次失败和视频冷启动问题，部署成功不能证明后续持续可用。仓库还存在需求、缺陷和优化建议混在同一待办池的问题，未统一优先级。

如果每日只拨测一次，会漏掉短时故障；如果每次异常都直接建 Issue，会产生重复单；如果让模型直接修改优先级或路线图，又会把规则噪声写进业务决策。

## 决策

把流程拆成三层：

1. GitHub Actions 每 15 分钟拨测生产公开只读页面，保存状态码、耗时、冷热样本和性能结果。
2. 确定性规则维护故障 Issue。同一端点与故障类型使用稳定指纹；连续失败才建单，故障期间更新原单，连续恢复后关闭，复发时重开。
3. 每天北京时间 09:00 在固定跟踪 Issue 中追加汇总，并读取未关闭 Issue，给出建议优先级、影响范围、依赖和方案。第一版不自动修改既有 Issue 的业务优先级、路线图或负责人。

第一版只覆盖网站公开链路，不覆盖视频播放和每日数据任务。巡检不读取 Cookie、Token、`.env` 或本地数据库。

收到 HTTP 响应前的统一 DNS、连接、TLS 或超时失败只说明本轮无法判断页面状态，不能证明每个页面同时故障。此类运行记为 `inconclusive`，不推进端点故障次数，只创建或更新一张入口故障 Issue。只有至少一个端点收到 HTTP 响应后，其他端点失败才按确定性页面故障处理。入口故障 Issue 在收到任意 HTTP 响应后开始累计恢复，连续 3 轮后关闭；500 或 502 也算入口连接已建立。

## 备选方案

- 每天只运行一次完整验收：请求少，但容易漏掉短时故障，无法区分偶发失败与持续故障。
- 每次失败立即建单：响应快，但会产生大量重复单和瞬时噪声。
- 由模型读取全部 Issue 后直接改标签和路线图：判断灵活，但规则不稳定，责任边界不清楚。
- 把网站可用性和每日数据任务放在同一个巡检中：覆盖更广，但故障归因和权限边界会混在一起。

## 后果

故障发现频率提高，Issue 可以作为持续故障的证据载体，固定日报便于比较每天的变化。代价是每 15 分钟产生一组公开请求，Actions 运行次数增加；巡检状态依赖 GitHub Issue 评论保存，若 Issue 被删除或状态评论被破坏，需要从下一轮重新累积连续次数。

性能阈值、优先级口径和巡检范围应先观察一段时间再调整。扩大到视频、数据任务或自动修改既有 Issue 时，需要新的决策记录。
