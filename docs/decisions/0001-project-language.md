# 建立项目级统一语言

- 状态：采用
- 日期：2026-11-11
- 关联：[项目统一语言表](../glossary.md)、Issue #20

## 背景

项目同时使用用户文案、外部理论词、代码字段和历史叫法。例如用户看到“N宗罪”，数据库使用 `memes`；`query pack` 是自建工程术语，而 query expansion 和 weak supervision 是外部理论词。仅依赖会话记忆会导致术语重新解释、命名漂移和实现边界混淆。

## 决策

建立 `docs/glossary.md` 作为项目术语的单一入口，并区分三类文档职责：

1. 词汇表负责定义、状态、边界和名称映射。
2. `docs/decisions/` 负责记录选择原因、备选方案和后果。
3. `docs/roadmap.md` 负责优先级、依赖和实施顺序。

影响需求、数据语义、分类口径或 UI 名称的新词，先在对话中提出候选定义；用户确认后再登记。会话可以保留临时理解，但正式术语以仓库词汇表为准。

## 备选方案

- 每个会话各自维护词汇表：上下文隔离好，但跨会话容易漂移，不采用。
- 把所有定义、决策和路线图放进一个文件：初期简单，但职责混杂、检索和修改成本会上升，不采用。
- 直接引入复杂术语管理或知识图谱工具：对当前规模过重，不采用。

## 后果

新会话需要先查阅词汇表，新增术语会多一次确认动作。作为回报，用户文案、代码标识、历史别名和外部理论词之间有了可追踪的映射，后续做 query pack、评论索引和语义文档时能够复用同一套语言。
