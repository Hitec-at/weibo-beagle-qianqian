# 每日生产巡检

更新日期：2026-11-17

## 目标

用固定、可复现的公开请求观察生产站点，区分可用性故障和性能退化。故障进入可追踪的 GitHub Issue；待办梳理只给建议，不直接改变既有路线图或负责人。

## 巡检范围

当前只检查生产公开只读链路：

- `/healthz`
- 首页
- N宗罪、粉丝二创、互动和高清图分类页
- 搜索页
- 真实 `/post/{id}` 详情；页面提供站内链接时自动发现，否则使用内置的稳定历史微博 ID
- 高清图页面中发现的真实 `/img` 代理地址
- 非新浪图片域名必须被 `/img` 拒绝

视频播放与每日数据任务不在第一版。巡检不读取 Cookie、Token、`.env` 或本地数据库。

## 运行方式

`.github/workflows/patrol.yml` 每 15 分钟运行一次，每次对页面做 3 个连续样本。首个样本标记为冷请求，后两个为热请求。图片代理和域名拦截检查各做 1 次。

`.github/workflows/patrol-daily.yml` 每天 01:00 UTC，即北京时间 09:00，运行汇总：

1. 汇总前一天北京时间全天的拨测轮次。
2. 列出端点失败、状态码和性能告警。
3. 读取全部未关闭 Issue，给出建议优先级、影响范围、依赖和建议方案。
4. 在固定的“每日巡检与待办梳理”Issue 中追加或更新当天报告。

固定日报 Issue 使用 `daily-patrol-tracking` 标签。机器状态保存在该 Issue 的专用元数据评论中，因此定时任务不依赖上一次 Actions 运行的内存或临时文件。

机器状态只保留当前北京时间自然日和前两个自然日的聚合样本，避免每 15 分钟一次的 p95 数据长期累积后超过 Issue 评论长度上限。日报需要的前一日数据始终保留。读取固定 Issue 的全部评论时使用 GitHub API 分页，不能依赖单页评论查询。

## 故障阈值

- 每次运行分为 `ok`、`fail` 和 `inconclusive` 三种结论。
- 如果所有目标端点都在收到 HTTP 响应前出现 DNS、连接、TLS 或超时错误，整轮记为“无法判断”。这种结果不增加端点故障次数，只创建或更新一张 `priority:P0` 的入口故障 Issue。
- 至少一个端点收到 HTTP 响应后，其他端点的失败才按确定性页面故障处理。
- 入口故障 Issue 使用稳定指纹 `entry:transport-unreachable`。连续不可达期间只更新原单；收到任意 HTTP 响应后开始累计恢复，连续 3 轮后关闭。
- 站点返回 500 或 502 表示 HTTP 连接已经建立，入口故障 Issue 会按恢复规则关闭；对应页面的错误继续按端点规则跟踪。
- 单次失败只写入机器状态，不建单。
- 同一端点连续 2 轮失败后创建故障 Issue。
- 同一端点连续 3 轮页面 p95 超过 2000 ms 后创建性能 Issue。
- 同一端点与故障类型使用稳定指纹，同一指纹只保留一个故障 Issue。
- 故障期间更新原 Issue，不重复建单。
- 连续 3 轮恢复后追加恢复记录并关闭；再次连续失败时重新打开原 Issue。

巡检请求失败与业务代码错误分开判断。部署成功、容器健康或 CI 通过都不能代替公开端点恢复。

“无法判断”不是健康状态。自动入口故障 Issue 会记录运行编号、失败层、错误类型和涉及端点数，并提示检查生产入口、DNS、TLS 证书和巡检节点网络。入口故障单是运行级告警，不代表每个页面都已独立故障。旧版状态中 2026-11-17 那次统一 TLS 失败已被一次性迁移为探测层异常，不计入端点连续故障。

## 优先级

巡检创建的故障 Issue 使用以下初始映射，最终修复优先级仍可人工调整：

- `/healthz` 不可用：`priority:P0`
- 首页、真实微博详情、搜索不可用：`priority:P1`
- 分类页、图片代理不可用：`priority:P2`
- 可用性正常但连续性能超过阈值：`priority:P2`

未关闭 Issue 的每日梳理仅输出建议。已有 `priority:P*` 标签优先保留；没有标签时按影响范围、Bug/需求和路线图关键词给出初稿。

## 数据与权限

- Actions 只申请 `contents: read` 和 `issues: write`。
- 故障 Issue 正文必须包含稳定指纹、最近 URL、状态码、耗时和检查时间。
- 巡检不得创建生产部署，也不得变更数据 Release。
- 同一仓库的拨测与日报共用 `production-patrol-state` 并发组，避免状态评论竞争。

## 人工接管

以下情况需要人工确认：

- 同一 Issue 的自动优先级与路线图冲突。
- 上游微博接口变化导致图片或页面持续失败。
- 需要扩大巡检范围到视频或数据任务。
- 连续告警但核心页面仍可用，需要调整性能阈值。

## 本地演练

只做生产只读拨测，不写 GitHub：

```bash
python patrol.py run --no-github --output /tmp/patrol-result.json
```

生成待办梳理 JSON，不修改 Issue：

```bash
GH_TOKEN="$(gh auth token)" python patrol.py triage --output /tmp/backlog-triage.json
```

不能用本地演练代替 Actions 首次手动运行。工作流合入后，应先手动运行一次拨测和一次日报，核对 Issue 去重、状态评论和日报内容，再观察定时运行。
